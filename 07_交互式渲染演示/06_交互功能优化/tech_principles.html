LagerNVS · Technical notes

两个「神经网络渲染」入口，底层是怎么做到的

门户里的 Live 和 Offline 并不是两套互不相干的模型。它们共享同一套 LagerNVS 前馈新视角合成网络；差别在于「这一帧像素是当场算出来的，还是事先算好再拿来交互」。

1. 要解决什么问题：新视角合成（NVS）

给你几张（甚至一张）场景照片，要生成相机移到别处之后「应该看到什么」。传统做法要么建显式 3D（网格 / 点云 / 体素），要么优化一个场景专用场（NeRF、3D Gaussian Splatting）。LagerNVS 走的是另一条路：

  • 前馈（feed-forward）：场景进来后一次编码，目标视角一次前向就能出图，不必为每个新场景长时间优化。
  • 无显式 3D 资产：不存 mesh / Gaussian；几何信息压在一组 latent scene tokens（潜在场景令牌）里，所以叫 Latent Geometry。
  • 可泛化：在大规模多视图数据上训好，野外照片也能估位姿并渲染。

2. 模型骨架：Encoder（重建器）+ Renderer（渲染器）

官方架构名 EncDecVitB/8：ViT-B 量级，patch size = 8。代码上就是 EncoderDecoder = Reconstructor + Renderer。

输入照片 I₁…Iₙ ↓ VGGT 系 Encoder（3D-aware） 潜在场景令牌 rec_tokens ← 场景被「记住」在这里 ↓ 目标相机的 Plücker 射线场 target_rays 12 层 Transformer Renderer（对 rec_tokens 做 cross-attention） ↓ 目标视角 RGB 图（sigmoid 输出到 [0,1]）

2.1 Encoder：VGGT 提「带几何偏见」的场景令牌

VGGT（Visual Geometry Grounded Transformer）在大量多视图几何任务上预训练，本身就会从图像里抽出对相机、深度、对应关系敏感的特征。LagerNVS 把它当作 Reconstructor：

  • 吃多张输入图（可无已知外参）；
  • 配合相机相关 token；
  • 输出每视图、每 patch 的特征向量，拼成 rec_tokens。

这一步只做一次（或切换场景时重做）。交互拖相机时不再重跑 Encoder，所以 Live 才能接近实时。

2.2 目标相机怎么告诉网络：Plücker 射线

新视角不是「给一张空白图让网络瞎猜」，而是给每个像素一条 Plücker 射线（用 6 维表示空间直线：方向 + 矩）。把整幅目标图像的射线排成 C×H×W 的射线图，再 PatchEmbed 成目标 token。网络看到的是：「在这个相机位姿下，每个图像块对应哪条空间射线」，从而把查询锚定到几何上——这就是论文说的 3D biases without explicit 3D。

2.3 Renderer：对场景令牌做交叉注意力「查询颜色」

Renderer.forward(rec_tokens, target_rays) 大致是：

  1. 射线图 → patch tokens（+ 少量 register tokens）；
  2. 经过 12 层 block：目标 token self-attn，并对 rec_tokens 做 cross-attn（General 模型常用 bidirectional cross-attention）；
  3. FinalLayer 把每个 patch 的隐向量解成 patch_size×patch_size×3 颜色，拼回整图。

直觉：目标视角的每个小块在问「场景记忆里和我这条射线最相关的外观是什么」，用注意力从 latent geometry 里读出颜色——渲染 = 条件生成，不是光栅化三角形。

3. Live 门户：同一套网络，边拖边渲

对应官方 Browser Viewer：run_interactive_server.py + interactive_viewer.html。

3.1 启动时（慢、做一次）

  • 加载 LagerNVS 权重 + VGGT；
  • 对 test_data/场景/ 里的照片 prepare_scene：估位姿、编码得到该场景的 rec_tokens；
  • 可选：把 model.renderer(...) 捕获成 CUDA Graph，避免每帧上百次 kernel 启动的 Python 开销。

3.2 交互时（快、每帧）

浏览器：拖拽 / WASD → 算出 4×4 相机矩阵 w2c → WebSocket 发给 GPU 服务 服务：w2c → Plücker rays → renderer(rec_tokens, rays) → RGB → JPEG 编码 → WebSocket 推回 浏览器：画到 canvas

状态栏里会区分 viewer FPS（含网络往返）和 GPU render FPS（纯推理）。隧道一差，你感觉「卡」，但往往是带宽/延迟，不是网络完全没在渲。

Live 的技术本质：神经网络推理循环 + 位姿流；像素是「现算」的，所以视角连续、自由度高，也必须有 GPU 作业在线。

4. Offline 门户：同一套网络，结果预烘焙再交互

对应本仓库的 offline_orbit_viewer.html + 预渲染静帧 / orbit 视频。

4.1 离线包是怎么来的

  • 用同一 LagerNVS（或评测管线）对固定相机轨迹批量渲染；
  • 产出 HQ 对比静帧（GT | Pred）、环绕 orbit、直线 path 等 mp4/png；
  • 写入 offline_manifest.json，本机 HTTP 静态托管。

4.2 浏览器里在干什么

不再跑神经网络。页面只是：切场景、显示静帧、对视频做时间轴 scrub（拖拽 ≈ 在预计算轨迹上滑动相机）。看起来像「交互渲染」，工程上是 交互式回放预计算神经渲染结果。

Offline 的技术本质：把 Live 里「每帧一次 renderer」提前做完并压成媒体；用交互 UI 掩盖「轨迹是锁死的」这一限制，换稳定、清晰、无 GPU。

5. 对照：为何观感不一样

  • 清晰度：Offline 的 HQ still 常是高 JPEG/PNG 评测分辨率；Live 受实时分辨率、JPEG 质量、隧道带宽限制。
  • 自由度：Live 任意位姿（未观测区域仍会糊/错）；Offline 只能走已渲轨迹。
  • 稳定性：Offline 只依赖本机文件服务；Live 依赖 Slurm 作业 + SSH/隧道。
  • 算力位置：Live = 远程 A100；Offline = 渲染已在过去发生，现在是 CPU/浏览器解码。

6. 与 NeRF / 3D Gaussian Splatting 的对比

  • NeRF：按场景优化 MLP 场，新场景要训很久；渲染是体积积分。
  • 3DGS：显式存大量高斯，光栅化快，但通常仍偏「每场景优化」。
  • LagerNVS：显式几何换成 latent tokens；用目标射线去 cross-attend 出颜色；训一次、推多场景；Live 交互靠「编码一次 + 反复渲染」。
